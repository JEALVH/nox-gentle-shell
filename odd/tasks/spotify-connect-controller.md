# Spotify Connect Active-Device Controller

## Objective and scope

The user chose a persistent Spotify row in Nox's detailed card and a TUI-only interactive overlay. Use Spotify Web API to read/control the **currently active** Connect device without reproducing audio locally. Exclude device enumeration/transfer, an audio-reactive spectrum, and new Spotify streaming.

## Constraints and checks

- Public Pi APIs; preserve existing telemetry, compact/off semantics, namespace ownership and width safety.
- Spotify PKCE with `127.0.0.1` loopback, state validation, least-privilege playback scopes, refresh, disconnect, and no token-bearing logs or session artifacts. Linux `secret-tool` keyring, otherwise memory-only; no plaintext persistence.
- Handle no active playback, revoked/restricted/offline, 429 backoff, paused state and cleanup. Attribute and link Spotify metadata.
- Strict TDD: explicitly selected in `odd/tasks/gentle-shell-visual-layer.md`. Focused `npx tsx --test test/<file>.test.ts`; full `npm test`; build `npm run build`; `git diff --check`.
- Technical artifacts in English. No commit, push or PR without explicit user authorization. Live OAuth/TUI validation requires an actual Spotify account and remains distinct from mock coverage.
- Visual polish (user selected both surfaces): frame the interactive overlay and improve Spotify's visual hierarchy within the persistent detailed card. Preserve width safety, telemetry, keyboard behavior, and existing playback semantics.
- Shared authentication (user authorized): one nonsecret `SPOTIFY_CLIENT_ID` configured in Nushell `config.nu` for new Pi sessions; refresh credentials stay in the OS keyring, never a shell script or plaintext file. Recover sessions across existing tabs and restarts, coordinate refresh/disconnect across processes, and make memory-only fallback explicit without leaking credentials.
